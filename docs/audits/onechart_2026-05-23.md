# OneChart chart-OCR A/B/C — 2026-05-23

P3.3-b: ships OneChart (`kppkkp/OneChart`) as a second chart-OCR
backend alongside the established DePlot path, behind the
ADR-0006 amendment that carves out the `trust_remote_code=True`
prohibition specifically for the chart-OCR slot when OneChart is
explicitly opted in.

This audit reports the three-way A/B/C comparison and the verdict.

## Setup

- **Reference rig**: RTX 4070 12 GB, vLLM 0.21 (`gpu_memory_utilization=0.68`
  during this eval — see "Resource pressure" below).
- **Corpus**: `tests/eval-data/slide-decks/queries.json` (CUDA new
  features & beyond deck, 109 pages, 245 figures, 30 queries).
- **Orchestrator**: Qwen3-8B-AWQ (`response_format` + xgrammar;
  sampling per `SamplingSettings`: temperature=0.1, top_p=0.8,
  presence_penalty=1.0, seed=42).
- **Answer prompt**: `answer/v3` (language-mirror directive + Path C
  schema bounds + positive worked example + system/user split).

## Configurations

| Config | Chart-OCR setting | Backend | Chart-extracted blocks in markdown |
|---|---|---|---|
| **A — Baseline** | `DISABLE_CHART_OCR=true` | (none) | 0 |
| **B — DePlot** | `DISABLE_CHART_OCR=false`, `MODELS__CHART_OCR=google/deplot` | Pix2Struct, ~600 MB | 50 stitched |
| **C — OneChart** | `DISABLE_CHART_OCR=false`, `MODELS__CHART_OCR=kppkkp/OneChart` | Custom Vary-derived, ~600 MB, `trust_remote_code=True` | **0** (every figure failed) |

Each config reparsed the CUDA deck via `memex parse <doc_id>` with
the listed env vars, reindexed via `memex index`, then ran
`memex eval` against the slide-decks queries.

## Results

| Config | ANS | refusal_cf | mcp_ans | HARD GATES |
|---|---|---|---|---|
| **A — Baseline** | **11/30** | 1.000 | 1.000 | ✓ |
| **B — DePlot** | 10/30 | 1.000 | 0.350 \* | ✓ |
| **C — OneChart** | **11/30** | 1.000 | 1.000 | ✓ |

\* DePlot's mcp_ans=0.35 is a known artifact: chart-extracted block
insertion changes chunk text, so chunk_ids (sha1[:10]) change too,
making the `relevant_chunk_ids` whitelist in queries.json stale.
ANS counts (which don't depend on chunk_ids) are the comparable
signal across configs. mcp_ans was 1.000 against the labeled
baseline before reparse.

## OneChart failure mode

**Every single figure triggered a CUDA device-side assertion** in
OneChart's forward pass:

```
CUDA error: device-side assert triggered
Search for `cudaErrorAssert' in https://docs.nvidia.com/cuda/cuda-runtime-api/
```

Earlier inspection (via direct `.chat()` invocation on a single
crop) traced the assertion to an `indexSelectSmallIndex` kernel
failure (`srcIndex < srcSelectDimSize`) accompanied by a friendly
reminder: *"the current text generation call has exceeded the
model's predefined maximum length (4096)"*. The 0.3B-param model's
autoregressive decoder cannot bound generation when the chart image
doesn't match its training distribution — it tries to generate
past its position-embedding budget and segfaults the CUDA context.
The first such failure corrupts CUDA state for the entire process;
all subsequent `.chat()` calls inherit the broken state and fail
identically.

**Defensive handling held**: the backend's try/except wrapper
(`except (OSError, RuntimeError)` → log + return empty markdown)
prevented the parse pipeline from crashing. Every figure produced
empty markdown; the stitch step left every `<!-- image -->`
placeholder unchanged. The resulting markdown is identical to the
baseline (no chart-OCR) state — which is why Config C's ANS / mcp_ans
match Config A exactly.

The pause-vLLM dance worked correctly: vLLM was paused before
OneChart loaded, the chart-OCR pass ran (and failed), the handle
was released, and vLLM restarted cleanly after.

## Verdict

**Plan decision matrix outcome (`OneChart ANS < 8 OR HARD GATES fail`)**:

OneChart didn't degrade HARD GATES (refusal_cf stayed at 1.000, no
hallucinations), but it produced **zero** usable chart extractions.
Functionally equivalent to no-chart-OCR on this corpus, with extra
load-time cost (~3 minutes to load the model + per-figure inference
attempts that all CUDA-asserted).

**Decision**: revert to DePlot-only as the documented chart-OCR
backend. **DePlot stays the default (off) per the original P3.3
verdict; OneChart stays in tree as a second backend behind the
ADR-0006 carve-out but is documented as known-broken on charts that
match the CUDA deck's profile.**

## Why this happened (deeper read)

OneChart was trained on standard public-benchmark chart datasets
(ChartQA, PlotQA, etc.) where chart images are clean rasterised
PNGs at predictable resolutions. The CUDA deck's figures pass
through Docling's classifier and emerge as Docling-cropped PDF
bboxes — non-trivially-sized, with embedded source-PDF idioms
(custom fonts, layered transparency, NVIDIA's design language).
The model's input pipeline likely encounters image tokens it
wasn't trained to handle, the language head generates degenerate
outputs that exceed position embeddings, and CUDA asserts.

This isn't a Memex integration bug — it's a model-robustness
limitation of OneChart on out-of-distribution chart imagery.

## ADR-0006 amendment outcome

The amendment **stays**. Reasons:
- The carve-out cost is near-zero (one paragraph in the ADR, ~80
  lines of code in the registry + backend).
- A future OneChart revision, or a different specialty chart model
  with a similar custom-architecture profile, could plug into the
  same dispatch branch.
- Reverting the amendment would also revert the code, and we'd
  have to re-add both the next time someone wants to try OneChart
  or a comparable model.
- The amendment is narrowly scoped (chart-OCR slot only, opt-in
  via env var, `reliable_check` gating) — there's no ongoing
  security cost to keeping it.

## What's NOT measured

- **OneChart on a chart-heavy corpus** (P3.3-c, blocked on source
  material). The CUDA deck has many photo-like / diagram-like
  figures even after Docling's pre-filter. A real financial-
  dashboard or scientific-figures PDF might exercise OneChart in
  its training-distribution and behave differently. This audit
  doesn't rule that out — it just shows that OneChart can't
  handle the CUDA deck's specific figure idiom.
- **A pinned older OneChart revision**. Upstream HF revision
  changes might fix the position-embedding-overflow issue. We
  loaded the current `main` revision. The dispatch supports a
  pinned `revision=` kwarg but we haven't tried older commits.
- **OneChart with a hard `max_new_tokens` guard**. OneChart's
  `.chat()` signature doesn't accept a `max_new_tokens` kwarg, so
  bounding generation would require dropping to the underlying
  `.generate()` method directly. Possible follow-up if a chart-
  heavy corpus surfaces.
- **DePlot's full ANS impact**. Config B's stale-label mcp_ans=0.35
  isn't a real quality regression — the ANS count of 10 (vs
  baseline 11) is the meaningful number, and it matches the
  prior P3.3 v6 verdict of −1 ANS on this corpus.

## Resource pressure

A side note from running this audit: vLLM's default
`gpu_memory_utilization=0.72` left no headroom when the eval
process loaded the embedder + reranker (2.1 GB) alongside the
DePlot- or OneChart-extended chunk content. Eval OOMed with
`CUDA out of memory. ... GPU 0 has a total capacity of 11.56 GiB
of which 48.69 MiB is free`. Reducing to
`MEMEX_VLLM_GPU_FRACTION=0.68` cleared the contention.

The 12 GB RTX 4070 reference rig is genuinely tight when running
the full stack + chart-OCR-stitched markdown. Worth documenting:
running `memex eval` with chart-OCR-enabled vault should use
`gpu_memory_utilization=0.68` (or lower) until VRAM contention
is otherwise addressed.

## Reproduction

```sh
# Setup: stop daemon, lower memory fraction
uv run memex daemon stop
MEMEX_VLLM_GPU_FRACTION=0.68 uv run memex daemon start

# Config A — baseline (no chart-OCR)
MEMEX_PARSE__DISABLE_CHART_OCR=true \
  uv run memex parse <cuda-doc-id>
uv run memex index <cuda-doc-id>
uv run memex eval tests/eval-data/slide-decks/queries.json

# Config B — DePlot
MEMEX_PARSE__DISABLE_CHART_OCR=false \
MEMEX_MODELS__CHART_OCR=google/deplot \
  uv run memex parse <cuda-doc-id>
uv run memex index <cuda-doc-id>
uv run memex daemon stop ; sleep 3 ; ...restart daemon...
uv run memex eval tests/eval-data/slide-decks/queries.json

# Config C — OneChart
MEMEX_PARSE__DISABLE_CHART_OCR=false \
MEMEX_MODELS__CHART_OCR=kppkkp/OneChart \
  uv run memex parse <cuda-doc-id>
uv run memex index <cuda-doc-id>
uv run memex daemon stop ; sleep 3 ; ...restart daemon...
uv run memex eval tests/eval-data/slide-decks/queries.json
```

## Next steps for chart-OCR

- **P3.3-c (chart-heavy corpus)** stays the highest-leverage
  remaining unblock. With a corpus where chart extraction
  materially helps, the trade-off Map flips. Without one, both
  DePlot's −1 ANS regression and OneChart's catastrophic failure
  argue for `disable_chart_ocr=True` as the default.
- **DePlot**: stays in tree as the documented chart-OCR backend.
  `MEMEX_MODELS__CHART_OCR=google/deplot` works; behavior matches
  the prior P3.3 v6 verdict.
- **OneChart**: stays in tree behind the ADR-0006 carve-out for
  future re-attempt on different corpora or upstream revisions.
  Documented as known-broken on CUDA-deck-style figures.
